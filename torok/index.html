Private · Go library

Torok runs agents that survive being interrupted.

Torok is a Go library for agents that use tools, and for workflows written as ordinary Go functions. You bring a model and your functions. Torok runs the tool loop, checks typed answers and commits progress, so a run resumes after a person answers a question or the process restarts. Desk runs on it.

add := tool.Func("add", "Add two numbers",
    func(_ context.Context, in numbers) (float64, error) {
        return in.A + in.B, nil
    }, tool.ReadOnly())

agent, err := torok.New(torok.Config{
    Instructions: "Use add for addition.",
    Model:        llm,
    Tools:        []tool.Tool{add},
})

result, err := agent.Run(ctx, "What is 19.50 plus 4.25?")
fmt.Println(*result.Value)

What it gives you

The shape is deliberately small: generic methods where a type belongs on a value, ordinary functions for behaviour, named configuration fields. There is no graph DSL, no builder chain and no hidden session handoff.

Plain Go

An agent is configuration: model, instructions, tools, checks. A workflow is a function of a context, a Flow and your input. A tool is func(ctx, In) (Out, error) with JSON tags. RunAs[T] names the answer type once, at the model boundary.

Progress that survives

A batch of model calls commits before any tool runs. Workflows replay from their checkpoints after a restart. A human question or an approval parks the run and frees the worker; the answer resumes it, once, even if it arrives twice.

One set of limits

Model calls, tool calls, steps, depth, concurrency, active time and tokens are set on the root and shared by every child. A spend ledger reserves money before the HTTP request and settles on the receipt, the rejection or an estimate.

Effects with receipts

Intent is committed before an effect starts. If the result is lost, the run waits for reconciliation rather than retrying blind. Tools are effectful unless the application promises otherwise, and an approval freezes the exact call it approves.

A resident service

For agents that stay on: a durable inbox with idempotent IDs, timers, bounded working memory, independent observers with their own freshness, daily admission budgets and pause. Idle waiting costs no inference.

Adapters, not a framework

Responses and Chat Completions. Stdio MCP with a frozen catalogue. Bounded HTTPS retrieval and processes. An HTTP and SSE control surface you mount inside your own server. Each one passes through the same accounting.

Runtime architecture

The engine sits between the application's functions and the store. Model and tool adapters are the only code that leaves the process, and both report to the same limits. The resident service and the HTTP adapter are optional layers on the same runtime. Neither adds a second execution engine.

Checked rather than promised

  • Race tests cover storage, sessions, typed repair, shared child limits, nested concurrency, approvals, ambiguous commits and event replay.
  • Child-process tests kill the process after a real effect and before its receipt is saved, then require reconciliation without repeating the effect.
  • A Lean 4 model of the acceptance boundary proves that a result is accepted only with an explained, passing check for every declared criterion, bound to that exact candidate and its original input. CI runs it and also checks that removing the guard makes the proof fail.
  • Model quality is a separate question. Scripted fixtures establish execution behaviour. What a live model does with the same tools has to be evaluated on real tasks with a budget and a human grader.

Status and contact

Torok is private and its API is experimental. It needs Go 1.27 and has three direct dependencies: an SQLite driver, a JSON Schema validator and a PDF text reader. If you want to compare notes on durable agents, or on what "accepted" should mean, send me a message.
