Private · Go agent harness

An agent harness in plain Go that survives a restart.

török /ˈtørøk/ · Hungarian for Turk. Named after Kempelen's chess automaton, the machine that played well because a person sat inside. Torok keeps the person in the loop on purpose.

Torok runs the tool loop, checks the typed answer and commits progress, so a run resumes after a person answers or the process comes back. You bring a model and ordinary Go functions. Desk runs on it.

Why Torok

Agents are work, not requests.

A run calls a model several times, runs your functions in between, spawns children, waits minutes or days for a person, and can be interrupted at any point. A request handler cannot hold that shape, and a model must not be trusted to remember it. Five small primitives carry the work instead.

Agent

Configuration, not a process

A model, instructions, tools and checks, built once. A question returns a typed answer. A failed check becomes repair feedback until the answer passes or the budget ends.

Tool

Your Go function, as it is

func(ctx, In) (Out, error) with a name and a description. Effectful by default. Read-only is a promise you make; approval is a stop you ask for, on the exact call.

Workflow

A path chosen in code

A function of a context, a Flow and your input. Steps record effects, children run in parallel, a question parks the run. The body replays from its checkpoints after a restart.

Runtime

One owner for progress and limits

Model calls commit before any tool runs; intent commits before an effect. One allowance on the root covers every child. Memory or SQLite underneath, an HTTP and SSE surface on top.

Resident

An agent that stays on

A durable inbox, timers, bounded memory, observers with their own freshness, daily admission budgets, pause. Idle costs nothing. Desk is one.

The whole shape fits in three statements. No graph DSL, no builder chain: generic methods where a type belongs on a value, plain functions for behaviour, named config fields.

// An ordinary Go function becomes a tool.
quote := tool.Func("quote", "Last close for a symbol", lastClose, tool.ReadOnly())

// A model and its tools become an agent.
analyst, err := torok.New(torok.Config{Model: llm, Tools: []tool.Tool{quote}})

// A question returns a typed, checked answer.
answer, err := analyst.RunAs[Close](ctx, "What did NVDA close at?")

Runtime architecture

The harness sits between your functions and the store. Model and tool adapters are the only code that leaves the process, and both report to the same limits. The resident service and the HTTP adapter sit on the same runtime. There is no second engine.

Checked rather than promised

  • Race tests cover storage, sessions, typed repair, shared child limits, nested concurrency, approvals, ambiguous commits and event replay.
  • Child-process tests kill the process after a real effect and before its receipt is saved, then require reconciliation without repeating the effect.
  • A Lean 4 model of the acceptance boundary proves that a result is accepted only with an explained, passing check for every declared criterion, bound to that exact candidate and its original input. CI runs it and also checks that removing the guard makes the proof fail.
  • Model quality is a separate question. Scripted fixtures prove execution. What a live model does with the same tools needs real tasks, a budget and a human grader.

About

Torok is the harness under Desk, which reviews an Interactive Brokers book on the market's clock and asks its owner only the questions that need a person. Private, experimental API, Go 1.27, three direct dependencies: SQLite, JSON Schema, a PDF reader. If you want to argue about what "accepted" should mean, get in touch.
